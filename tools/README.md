# Управление GitHub и VDS для Rhisseth

В этой папке находятся локальные PowerShell-скрипты для безопасного управления проектом между локальным репозиторием, GitHub и VDS.
Каталог `tools/` добавлен в `.gitignore`, поэтому скрипты и эта инструкция не отправляются в репозиторий.

## Требования

- Windows PowerShell 5.1 или PowerShell 7;
- Git установлен и доступен в `PATH`;
- выполнена авторизация GitHub через Git Credential Manager или SSH;
- запуск из каталога репозитория `C:\Avalon-repo\rhisseth.ru` либо из папки `tools`.

## Sync-FromGitHub.ps1

Сравнивает текущую локальную ветку с одноимённой веткой на GitHub.

Проверки и действия:

- останавливается при наличии незакоммиченных изменений;
- получает свежие данные командой `git fetch`;
- выполняет только безопасное обновление `git pull --ff-only`, если GitHub новее;
- сообщает, если локальная ветка новее или версии совпадают;
- сообщает, если удалённая ветка ещё не создана.

Запуск:

```powershell
.\tools\Sync-FromGitHub.ps1
```

Для конкретной ветки:

```powershell
.\tools\Sync-FromGitHub.ps1 -Branch release/0.0.2
```

## Publish-ToGitHub.ps1

Отправляет локальные изменения в GitHub и автоматически создаёт удалённую ветку при первой публикации.

После запуска скрипт предлагает выбрать действие:

1. создать релиз — показывает последний Git-тег, запрашивает новый номер формата `0.0.0`, создаёт тег `v0.0.0` и отправляет его на GitHub;
2. отправить данные без создания релиза.

Перед публикацией скрипт:

- получает свежие данные GitHub;
- останавливается, если удалённая ветка содержит более новые коммиты;
- добавляет изменения командой `git add -A`;
- создаёт коммит и отправляет ветку через `git push`.

Запуск:

```powershell
.\tools\Publish-ToGitHub.ps1
```

Для конкретной ветки:

```powershell
.\tools\Publish-ToGitHub.ps1 -Branch release/0.0.2
```

## Рекомендуемый порядок работы

1. Перед началом работы запустить `Sync-FromGitHub.ps1`.
2. Внести и проверить изменения в проекте.
3. Запустить `Publish-ToGitHub.ps1`.
4. Для объединения релиза с `main` создать на GitHub Pull Request с направлением:
   `release/0.0.2` → `main`.

## Авторизация

Скрипты не хранят пароли, токены или ключи. Git использует заранее настроенный Git Credential Manager или SSH-ключ.

Для первичной настройки Git Credential Manager:

```powershell
git credential-manager github login
```

## Проверка и публикация на VDS

Репозиторное дополнительное правило публикации описано в
[`docs/policies/rhisseth-publication-rule.md`](../docs/policies/rhisseth-publication-rule.md).
Оно рекомендуется для рабочих мест с доступом к runner и Passbolt, но не
является обязательным на других компьютерах.

`vds-credentials.example.json` — шаблон конфигурации SSH. Скопируйте его в `vds-credentials.json`, укажите путь к закрытому ключу и удалённый каталог. Файл `vds-credentials.json` исключён из Git.

`Check-VdsChanges.ps1` получает снимок проекта с VDS и при отличиях сохраняет их отдельным коммитом в ветке `elvizzz`.

`Compare-Deployment.ps1` сравнивает одинаковый набор проектных файлов и выводит
точный список расхождений: `M` — изменён на VDS, `A` — добавлен на VDS,
`D` — отсутствует на VDS. Серверные `.env`, секреты, backup, отчёты,
временные файлы и кэш симметрично исключаются из сравнения.

`Publish-ToVds.ps1` упаковывает выбранную Git-ветку и загружает её на VDS после явного подтверждения `YES`.

```powershell
Copy-Item .\tools\vds-credentials.example.json .\tools\vds-credentials.json
.\tools\Check-VdsChanges.ps1
.\tools\Publish-ToVds.ps1 -Branch main
```

Удалённые операции с инфраструктурой должны запускаться через утверждённый runner проекта (`STU-AUTOMATION-01`) согласно правилам репозитория. Скрипты не записывают пароли и токены в файлы или команды.

### Check-VdsChanges.ps1

Скрипт проверяет, не изменялись ли файлы проекта вручную на VDS:

- читает параметры подключения из `vds-credentials.json`;
- создаёт временный архив проекта на VDS;
- скачивает архив через `scp` и удаляет временный файл с сервера;
- создаёт чистый снимок текущего локального Git-коммита;
- сравнивает снимок Git с данными VDS, исключая `.git`;
- если отличий нет — завершает работу без изменений;
- если отличия есть — создаёт или открывает локальную ветку `elvizzz`, копирует данные VDS и создаёт коммит с отметкой времени.

После выполнения следует проверить изменения:

```powershell
git status
git log --oneline -5
git diff main..elvizzz
```

### Publish-ToVds.ps1

Скрипт публикует выбранную Git-ветку на VDS:

- проверяет наличие файла конфигурации и SSH-ключа;
- проверяет отсутствие незакоммиченных изменений;
- запрашивает явное подтверждение `YES`;
- создаёт архив выбранной Git-ветки командой `git archive`;
- распаковывает его в каталог `RemotePath` на VDS;
- не отправляет `.git`, `tools` и другие файлы, отсутствующие в выбранном коммите.

Перед публикацией рекомендуется выполнить `Check-VdsChanges.ps1`, чтобы не потерять ручные изменения сотрудника.

### Файлы конфигурации VDS

- `vds-credentials.example.json` — безопасный шаблон;
- `vds-credentials.json` — рабочая локальная конфигурация, исключённая из Git;
- `VDS-SSH-SETUP.md` — отдельная подробная инструкция по настройке ключа и автоматического подключения.

## Полный рабочий процесс без участия ИИ

Отчёты именно этого инструмента синхронизации сохраняются в:

```text
C:\Avalon-repo\rhisseth.ru\reports\Git-sync\
```

Каталог создаётся автоматически при первом выполнении команды.

Все команды выполняются из PowerShell в корне репозитория:

```powershell
Set-Location C:\Avalon-repo\rhisseth.ru
```

Для интерактивного режима запустите:

```powershell
.\tools\rhisseth-sync.ps1
```

Меню выполняет единый рабочий процесс:

1. сравнить локальную ветку, одноимённую ветку GitHub и код VDS;
2. получить GitHub только fast-forward, когда GitHub новее;
3. создать коммит либо релиз и отправить локальную ветку в GitHub;
4. развернуть на VDS именно подтверждённый `origin/<ветка>` после резервного копирования;
5. импортировать VDS в отдельную ветку `vds/import-YYYYMMDD-HHMMSS`, создать коммит, отправить ветку в GitHub и вернуться в исходную ветку;
6. выбрать резервную копию VDS по дате и восстановить её;
7. перезапустить службы и выполнить health-check;
8. выйти.

Секреты и служебные данные (`.env`, `secrets`, `reports`, `temp`, backup и кэш) не включаются в импорт VDS и сравнение кода.

### 1. Первичная настройка

1. Установите Git, PowerShell 5.1/7 и OpenSSH (`ssh`, `scp`), добавьте их в `PATH`.
2. Настройте GitHub Credential Manager или SSH. Пароли и токены в скрипты не записываются.
3. Скопируйте `vds-credentials.example.json` в `vds-credentials.json`, заполните путь ключа и удалённый каталог.
4. Один раз проверьте `ssh ... hostname` по инструкции `VDS-SSH-SETUP.md`.

### 2. Получить изменения с GitHub

```powershell
.\tools\Sync-FromGitHub.ps1 -Branch main
```

Скрипт выполняет `fetch` и только fast-forward обновление. При расхождении веток он останавливается: сначала решите конфликт вручную.

### 3. Проверить три источника

```powershell
.\tools\Compare-Deployment.ps1 -Branch main
```

Команда показывает commit локальной ветки, commit GitHub, количество коммитов впереди/позади и различия файлов на VDS. Это read-only проверка.

Каждый Markdown-отчёт, который `rhisseth-sync.ps1` создаёт в `reports/Git-sync/`, содержит полный SHA и отдельное поле `Комментарий коммита` с точным текстом, который оператор ввёл при создании коммита. Для пунктов 3 и 5 этот комментарий обязателен и используется как тема commit без подмены стандартным текстом. Если `HEAD` отсутствует, отчёт явно указывает, что commit не создан.

### 4. Опубликовать обновление на GitHub

```powershell
.\tools\Publish-ToGitHub.ps1 -Branch main
```

Скрипт предлагает создать commit и, при выборе релиза, тег `vX.Y.Z`. После ручной проверки релизную ветку следует объединить с `main` через Pull Request. Для каждого нового релиза создайте запись в `docs/releases/` согласно `rhisseth.ru/AGENTS.md`.

### 5. Опубликовать исправление на VDS

Сначала убедитесь, что ручных изменений на VDS нет:

```powershell
.\tools\Check-VdsChanges.ps1
.\tools\Compare-Deployment.ps1 -Branch main
.\tools\Publish-ToVds.ps1 -Branch main
```

`Publish-ToVds.ps1` требует явного `YES`, перед распаковкой создаёт архив `/var/backups/rhisseth/rhisseth-YYYYMMDD-HHMMSS.tgz`, загружает архив Git без `.git` и удаляет только временный архив из `/tmp`. Опция `-SkipBackup` предназначена только для аварийного сценария и не рекомендуется.

### 6. Забрать ручные изменения с VDS

```powershell
.\tools\Sync-FromVds.ps1 -SourceBranch main -Push
```

Скрипт не смешивает данные с рабочей веткой: создаёт отдельную ветку с отметкой времени, коммитит снимок VDS, отправляет ветку в GitHub и возвращается в исходную ветку. После проверки создайте Pull Request в `main` либо перенесите нужный коммит вручную.

Пункт 5 также выполняет read-only экспорт всех данных, изменяемых через административные редакторы: гексов, военных юнитов и их цен/апгрейдов, ресурсов, дополнительных построек и их размещений, генералов. Санитизированный снимок сохраняется как `data/snapshots/editable-database.json`; пользователи, сессии, кошельки, склады и история боёв не экспортируются. После проверки и объединения импортной ветки штатный мигратор применяет снимок после SQL-миграций.

### 7. Восстановление VDS

Список архивов:

```powershell
ssh -i $cfg.KeyPath "$($cfg.User)@$($cfg.Host)" "ls -lh /var/backups/rhisseth"
```

Восстановление выполняйте только после остановки приложения и проверки архива:

```bash
mkdir -p /opt/rhisseth/repository.restore
tar -xzf /var/backups/rhisseth/rhisseth-YYYYMMDD-HHMMSS.tgz -C /opt/rhisseth/repository.restore
```

Затем переключите приложение на восстановленный каталог по вашей штатной процедуре. Скрипт намеренно не перезапускает systemd/Docker-сервисы автоматически.

## Правила безопасности

- Перед публикацией на VDS всегда выполняйте `Check-VdsChanges.ps1` или `Compare-Deployment.ps1`.
- Не используйте `git push --force`, `tar` с удалением каталога или передачу секретов в командной строке.
- Рабочий `vds-credentials.json` и приватный ключ не должны попадать в GitHub.
- Не удаляйте резервную копию, пока новая версия не проверена на сайте.
- Скрипты выполняют только подготовку/копирование файлов; миграции базы данных, смена секретов и перезапуск сервисов выполняются отдельно по инструкции приложения.
