# Предложение по веб-версии и VPS

Рекомендуемый первый этап: сохранить SVG-слой гексов поверх готового PNG,
HTML/CSS/JavaScript, Python FastAPI и PostgreSQL 18. Это сохраняет существующую
механику и позволяет отдельно развивать API. Контейнер приложения собран
по подходу из [документации FastAPI](https://fastapi.tiangolo.com/deployment/docker/).

| Вариант | Когда выбирать |
|---|---|
| Текущий интерфейс + FastAPI | Рекомендуется для быстрого переноса карты и редактора |
| Vue/React + FastAPI | Следующий этап для кабинета, нескольких карт и сложного редактора |
| Django + PostgreSQL | Если приоритет — встроенная админка, пользователи и справочники |

Следующий этап интерфейса: масштабирование и перемещение карты, поиск по Q/R,
фильтры ресурсов и местности, сенсорное открытие карточки, режим просмотра,
роли viewer/editor/admin. До многопользовательского редактора добавить журнал
изменений и optimistic locking: устаревшая версия гекса должна возвращать 409.
OpenAI подключать через отдельный worker с PostgreSQL-очередью, лимитами расходов
и сохраняемыми версиями PNG; не запускать платный запрос после каждого поля.

Первый тестовый VPS по решению пользователя: 1 vCPU, 1 GB RAM, Ubuntu 24.04 LTS.
Подготовлен `deploy/compose.test.yml` с одним worker и ограничениями памяти.
Это конфигурация для малой тестовой нагрузки; ёмкость пока не измерена.
Предложение для дальнейшего VPS: 2 vCPU, 4 GB RAM, 40–60 GB SSD.
Для нескольких активных редакторов и фоновых задач — 4 vCPU,
8 GB RAM после замеров. GPU для внешнего API не требуется.

На VPS: SSH по ключам, отдельный sudo-оператор, проверенный host key,
обновления ОС, время UTC, firewall с SSH только от разрешённого контроллера,
публичные TCP 80/443. PostgreSQL и API не публикуются портами Docker.
Членство в группе docker равнозначно широким правам на сервер.
Сначала проверить вход по ключу, затем отключать password/root SSH.
Не применять сетевые изменения до проверки запасного доступа.

DNS A направить на VPS; AAAA создавать только при рабочем IPv6.
Caddy получает и обновляет TLS при корректном DNS и доступности 80/443:
[Automatic HTTPS](https://caddyserver.com/docs/automatic-https).
Для staging использовать отдельный домен и базу. Приложение пока работает
под владельцем базы: перед расширением доступа выделить ограниченную SQL-роль.

Ежедневно: дамп базы, SHA-256, копия вне VPS, контроль выполнения и места на диске.
Первичная цель: RPO 24 часа, RTO 2 часа после проверенного восстановления.
Для меньшего RPO потребуется WAL/PITR. Эти значения являются предложением.
Проверять /health, HTTPS, доступность карты и восстановление копий.
Версии зависимостей ограничены диапазонами; перед production зафиксировать
проверенный lockfile и digest образов для воспроизводимого выпуска.
