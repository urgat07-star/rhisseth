# Задача: резервное копирование и переносимое развертывание Rhisseth

Дата постановки: 2026-09-16. Статус: согласована, ожидает реализации.
Заказчик согласовал требования в переписке. Этот документ является задачей;
его создание не означает выполнение изменений на серверах.

## Цель и область работ

Обеспечить восстановление проекта из утвержденного GitHub Release и полного
архива данных на Ubuntu 24.04 с ресурсами не ниже 1 vCPU, 1 ГБ RAM и 10 ГБ диска.
Исходный экземпляр: `62.113.109.168`. Репозиторий: `urgat07-star/rhisseth`.
Целевая ВМ может содержать другое ПО: проверка совместимости обязательна.
Минимальный размер диска не гарантирует достаточного свободного места при росте данных.

## Резервное копирование

1. Инвентаризировать фактические данные действующего экземпляра: полную БД
   PostgreSQL, пользователей и права приложения, файлы вне Git, загрузки,
   необходимые конфигурации и секреты. Зафиксировать точный состав и исключения.
2. Выполнять полный согласованный бэкап ежедневно в 06:00 `Europe/Moscow`.
   Допустимая потеря данных — до суток; отдельный предельный срок восстановления
   заказчиком не установлен. Измерить время восстановления при испытании.
3. Создавать отдельный переносимый архив на каждый запуск. Включать согласованный
   дамп БД, файлы и настройки, необходимые для восстановления, а также манифест
   с временем UTC/МСК, версией схемы, тегом/SHA приложения и контрольными суммами.
   Код и пакеты восстанавливать из GitHub и фиксированных зависимостей.
4. Обеспечить согласованность дампа и связанных изменяемых файлов; документировать
   необходимость и фактическую продолжительность приостановки записи, если она нужна.
5. Передавать архив по SSH на `185.216.87.44` в создаваемый каталог
   `/srv/backups/rhisseth`. Доступ получить из Passbolt без вывода секретов.
   Создать отдельный доступ автоматизации с необходимыми правами, сохранив доступ root.
6. По явному решению заказчика архивы не шифровать. Ограничить доступ к каталогу
   и архивам; секреты из архивов не публиковать в Git, отчетах или журналах.
7. Хранить копии за последние семь дней. Удалять устаревшие копии только после
   успешной передачи и проверки новой; при сбое сохранять последнюю пригодную копию.
   Не включать незавершенные архивы в список доступных для восстановления.
8. Проверять передачу и целостность, публиковать готовый архив атомарно.
   Последним считать успешно завершенный и проверенный архив, а не файл по mtime.
   Ограничить локальные временные копии и исключить одновременные запуски.
9. Рассмотреть и описать альтернативы: дамп/архив по SSH (выбран), снимок ВМ,
   физический бэкап/PITR, объектное хранилище. Дополнительные варианты не внедрять
   без отдельного решения заказчика.

## Утверждение версий

Владелец GitHub-репозитория утверждает версию публикацией GitHub Release
с версионным тегом, например `v1.0.0`, после проверки изменений.
Развертывание использует последний опубликованный утвержденный Release;
draft и prerelease исключаются. Не подменять отсутствие Release веткой main.
Предусмотреть выбор конкретного утвержденного релиза для воспроизводимости.
Фиксировать тег и точный SHA; документировать ограничения прав публикации
и защиты тегов, запрет перезаписи утвержденной версии и порядок отката.
Доступ к GitHub для private repo — отдельный read-only доступ, без секретов в URL.

## Автоматическое развертывание и восстановление

1. Реализовать отдельные проверяемые скрипты и конфигурационные шаблоны.
   Поддержать безопасный повторный запуск, блокировку параллельных операций,
   явное описание фаз и остановку при ошибке. Не затирать существующие данные.
2. До установки пакетов и иных изменений выполнить read-only preflight:
   ОС/архитектура и поддерживаемость, CPU/RAM, свободное место с учетом размера
   архива и распаковки, sudo, сеть, DNS, доступ к GitHub и архивам, версии ПО,
   службы, процессы, порты (включая 80, 443, 5432, 8080), конфигурации, каталоги,
   существующие БД и сайты. Проверять фактическое использование ПО, а не только
   его наличие. Документировать поддерживаемые архитектуры.
3. При занятых требуемых портах, используемых конфликтующих службах, недостатке
   ресурсов или иной несовместимости остановиться до изменений. Представить
   заказчику подробный санитизированный отчет: что занято, чем используется,
   доказательства, причина остановки и варианты устранения. Не останавливать
   чужие службы и не изменять их конфигурации автоматически.
4. При успешном preflight продолжить без дополнительного подтверждения.
   Совместимое неиспользуемое ПО допускается переиспользовать после проверки;
   установить все недостающие системные и Python-зависимости, необходимые
   для приложения, БД, nginx, TLS, Git, SSH, архивации, бэкапа и проверок.
   Использовать фиксированные зависимости приложения и учитывать 1 ГБ RAM.
5. Получить утвержденный Release и последний проверенный архив, проверить
   контрольные суммы, состав, безопасность путей при распаковке и совместимость
   схемы БД с релизом. Перед изменениями данных выполнить проверенные миграции;
   при неподдерживаемой комбинации остановиться с отчетом.
6. Восстановить БД, необходимые файлы и настройки, настроить службы и автозапуск.
   Переносимые настройки отделить от привязанных к исходной ВМ. Не импортировать
   стартовые данные поверх восстановленной БД. Описать откат при частичном сбое.
7. Домен `rhisseth.ru`, параметры HTTPS и другие параметры экземпляра вынести
   в отдельный конфигурационный файл на ВМ. Заказчик может изменить адрес
   без редактирования скриптов. Документировать команду применения конфигурации,
   проверку DNS, выпуск/обновление сертификата, проверку и reload nginx.
   Использовать доверенный публичный сертификат для рабочего домена.
8. Автоматическое изменение DNS в эту задачу не входит. На тестовой ВМ
   не переключать рабочий домен и не затрагивать production. Проверить HTTPS
   с явно описанным тестовым способом доступа и ограничениями проверки DNS/TLS.

## Контроллер и обязательный runner

Уточнение владельца от 16.09.2026 для публичного VDS Rhisseth:
`10.210.52.128` является одним из маршрутов. При его недоступности использовать
локальный Docker с закреплённым SSH host key и проектным журналом; см.
[ранбук TLS](../runbooks/letsencrypt-tls.md). Правила ниже для внутренних
ВМ описывают прежний инфраструктурный маршрут и не запрещают этот доступ к VDS.

Текущие операции выполнять через `STU-AUTOMATION-01` (`10.210.52.128`),
используя закрепленное SSH-соединение и проверенные отдельные скрипты.
Рабочая станция только передает скрипты и получает санитизированные результаты.
Все обращения к внутренней ВМ и Passbolt выполняются с runner.

Предусмотреть переносимый запуск с другого контроллера: описать ОС, утилиты,
версии, SSH-ключи/known_hosts, доступы, сетевые требования и получение секретов.
Документировать, нужен ли Docker или иной дополнительный компонент; не делать
Docker обязательным без технической необходимости. Переносимость скрипта
не отменяет действующую политику обязательного runner для внутренних операций.
Суточное расписание и его зависимости явно описать, включая поведение при
недоступности контроллера, источника или хранилища и порядок повторного запуска.

Каждая runner-операция создает Markdown-журнал в
`reports/automation-logs/YYYY-MM-DD/`: UTC/МСК, идентификатор задачи,
контроллер, runner, точные цели/тип действия, preflight, санитизированный вывод,
exit code, результат проверки, изменения/перезагрузки и IDs ресурсов Passbolt.
Сбой журналирования останавливает мутации. Не писать секреты, полный JSON
Passbolt, дампы окружения или команды с секретами.

## Испытание и критерии приемки

Испытательная ВМ: `avalon@10.210.52.79`, доступ через обязательный runner.
Получить ее доступ безопасно; сначала выполнить preflight. Если ВМ занята
или не соответствует требованиям, представить отчет и не проводить развертывание.

- На исходном VPS настроен полный ежедневный бэкап в 06:00 МСК;
  проверены успешный запуск, передача, отказ при сбое и хранение за неделю.
- На SSH-хранилище создан каталог и отдельный доступ автоматизации,
  root сохраняет доступ; архив пригоден для независимого переноса.
- На тестовой ВМ выполнено развертывание утвержденного Release и восстановление
  фактического архива; зафиксированы имя архива, время, тег и SHA.
- Проверены схема и содержимое БД, количество/контрольные суммы данных,
  пользователи и права, вход, чтение и изменение данных, frontend/статика,
  API, nginx/HTTPS и сохранность после рестарта служб и перезагрузки тестовой ВМ.
  Тестовые записи удалены либо выполняются в отдельной тестовой области.
- Проверены повторный запуск без потери данных, отказ при конфликте порта,
  поврежденном архиве, отсутствии утвержденного Release и несовместимости схемы.
  Негативные проверки не затрагивают рабочие сервисы.
- Изменение домена через конфигурационный файл и применение настроек описаны
  и проверены безопасным тестовым способом.
- Представлен отчет после восстановления с результатами каждого критерия,
  временем восстановления, ресурсами и ограничениями; непроверенное явно отмечено.
