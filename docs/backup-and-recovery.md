# Бэкап и восстановление Rhisseth

Задача: [требования и приемка](tasks/backup-and-portable-deployment.md).
Пошаговые команды и необходимый софт для администратора:
[восстановление без ИИ](manual-recovery.md).

Текущий источник — `62.113.109.168`, SSH-хранилище — `185.216.87.44`,
испытательная ВМ — `10.210.52.56`. Текущее выполнение только через
`STU-AUTOMATION-01` (`10.210.52.128`). Секреты не передавать в чат, Git или argv.

## Состав и выбранный вариант

Выбран полный логический дамп PostgreSQL 16 (`pg_dump -Fc`) и `.tar.gz` по SSH.
Включаются все таблицы приложения, пользователи, bcrypt-хеши, роли, сессии,
схема и данные; содержимое `/opt/rhisseth` вне воспроизводимого кода/runtime,
включая secrets, temp, previews и новые каталоги данных; текущие конфигурации
nginx, systemd приложения и PostgreSQL. Конфигурации исходной ВМ — доказательство
и материал для переноса, они не применяются поверх настроек новой ВМ.
Архив не является образом ОС и не содержит посторонние базы/сайты/службы.
При появлении данных вне `/opt/rhisseth` требуется дополнить инвентаризацию.

Не включаются Git checkout, venv, старые бэкапы, рабочий spool, логи и
automation scripts: их версии хранить отдельно в Git. В архиве есть `manifest.json`
с SHA исходного кода, схемой, SHA256 каждого обычного файла, сигнатурами таблиц
и временем UTC. Миграции, уже примененные в БД, также получают контрольные суммы.
Дамп не переносит серверные пароли/привилегии PostgreSQL: восстановление создает
отдельную ограниченную роль и новый пароль, сохраняя права пользователей сайта.
Исходные секреты сохраняются в закрытом `secrets/source-secrets` для владельца.

Для согласованности приложение останавливается на время дампа и копирования
изменяемых файлов, затем возобновляется до сжатия и передачи. На сайте в эту
паузу возможны ошибки nginx 502. Другие приложения не должны писать в проектную
БД/файлы во время копирования; при появлении таких писателей пересмотреть механизм.
Суточные копии допускают потерю почти 24 часов данных.

Снимок ВМ быстрее возвращает всю ОС, но зависит от гипервизора и захватывает
постороннее ПО. Физический бэкап с WAL/PITR уменьшает возможную потерю данных,
но требует дополнительного места и обслуживания. S3 дает независимое хранилище
с версионированием; для этой задачи выбран существующий сервер по SSH.

## Хранение, доступы и расписание

Каталог: `/srv/backups/rhisseth`, права `0700`. Владелец — `rhisseth-backup`;
root сохраняет доступ. Родитель `/srv/backups` допускает проход (`0711`).
В `authorized_keys` установлен отдельный ключ с `restrict` и принудительной
командой `/usr/bin/python3 /usr/local/lib/rhisseth/rhisseth_storage.py`.
Доступ не предоставляет shell, SFTP, forwarding или произвольные пути.
Протокол: `list`, `get <имя>`, `put <имя> <размер> <sha256>`.
Ключ находится только на runner в `.local/recovery/storage-key` (`0600`).
Passbolt используется на runner для исходного VPS и административной настройки;
хранилище в суточном запуске принимает выделенный ключ.

Архивы по решению заказчика **не шифруются**; SSH защищает передачу.
Архив содержит секреты и персональные данные, его нельзя публиковать.
Закрытый каталог не защищает от администратора/компрометации сервера хранения.
Ключ автоматизации может читать архивы; ограничивать доступ к самому runner.

После проверки длины и SHA256 архив публикуется атомарно, затем создается
JSON-квитанция готовности. Для выбора учитывается время завершения из квитанции.
Незавершенные файлы не восстанавливаются. Удаляются успешно завершенные копии
старше семи дней, только после успешной новой передачи. При сбое старые копии
сохраняются. Локально сохраняется максимум последняя завершенная, еще не
переданная копия; после успешного round-trip она удаляется. Рабочие файлы runner
имеют owner-only права и очищаются после операции.

На runner установлены `rhisseth-backup.service` и `rhisseth-backup.timer`:
`OnCalendar=*-*-* 06:00:00 Europe/Moscow`, `Persistent=true`.
При выключенном runner пропущенное расписание запускается после включения.
При ошибке запуска автоматическая рассылка и частые повторы не настроены:
устранить причину и повторить службу вручную. Нужны сеть, доступ к Passbolt,
источнику и SSH-хранилищу. Одновременные операции блокируются flock.

Команды **на runner**:

```bash
systemctl list-timers rhisseth-backup.timer --no-pager
systemctl show rhisseth-backup.service -p Result -p ExecMainStatus
sudo systemctl start rhisseth-backup.service
python3 /home/avalon/rhisseth.ru/scripts/automation/Run-RhissethRecovery.py list
```

С рабочей станции используется только закрепленный контрольный канал:

```powershell
pwsh -File scripts/automation/Invoke-RhissethRecovery.ps1 -Operation list
pwsh -File scripts/automation/Invoke-RhissethRecovery.ps1 -Operation run-scheduled
```

## Утверждение версии

Обычный режим получает GitHub Releases через API, исключает draft/prerelease,
проверяет автора публикации по ID владельца репозитория и выбирает последнюю
публикацию. Поддерживаются версии `0.0.1`, `v0.0.1`, `release/0.0.1`.
При отсутствии утвержденного Release выполнение останавливается; main не используется.
Пока реализована выборка первых 100 Releases; архив старых релизов за этой границей
не участвует в автоматическом выборе.

Порядок владельца GitHub:

1. Проверить PR и результаты проверок, выбрать принятый коммит.
2. Открыть **Releases → Draft a new release**, выбрать уникальный тег `v0.0.1`
   и принятый commit/branch как Target, описать изменения и совместимость схемы.
3. Опубликовать обычный Release от своего аккаунта; публикация означает утверждение.
4. Ограничить создание/изменение release-тегов правилами репозитория и включить
   неизменяемость релизов, если доступна. Не перезаписывать опубликованную версию.

В текущей сессии владелец явно выбрал `release/0.0.1`. Если это ветка,
испытание может использовать ее **только с явным выбором** и фиксацией SHA;
это не включает автоматическое доверие ко всем release-веткам. Для дальнейшего
автоматического выбора нужно опубликовать GitHub Release. Тег и SHA записываются
в `release.json`, `recovery.json` и журнал. Контроллер проверяет совместимость
схемы, формирует архив принятого Git checkout и передает его на ВМ вместе с SHA256.
Так Git не требуется на ВМ до установки зависимостей.

## Проверки и восстановление

Поддерживается Ubuntu 24.04 x86_64, минимум 1 vCPU/1 ГБ RAM/10 ГБ номинального
диска. Проверка учитывает минимум 900 МиБ видимой ОС памяти, поскольку на исходной
ВМ 1 ГБ отображается как 961 МиБ. Swap не заменяет RAM. Нужны root/sudo и Python 3.12
(штатный Ubuntu), доступ к Ubuntu/PyPI; максимальный архив/распакованные данные
в текущем формате — 8 ГиБ. Требуется свободное место для данных, БД и установки,
поэтому 10 ГБ не является гарантией при любом объеме данных. Сложность расчета
сигнатур таблиц ограничивает применимость к очень большой БД; для роста нужен
потоковый механизм проверки и отдельное испытание ресурсов.

До изменений проверяются ОС/архитектура, CPU/RAM, свободный диск, порты
80/443/5432/8080, активные службы, сайты nginx, существующие данные/кластер PostgreSQL,
учетная запись rhisseth и каталог проекта. Занятый ресурс блокирует установку
с отчетом `ss -lntp`, состояниями служб и списком конфликтов. Чужие службы не
останавливаются. Уже установленное совместимое неиспользуемое ПО можно использовать;
существующий кластер PostgreSQL даже в остановленном состоянии требует разбора.

После preflight проверяются SHA256 архива, все обычные файлы, безопасные пути,
схема БД и миграции релиза. Не поддерживаются внешние project symlinks;
конфигурационные symlinks являются доказательством и не распаковываются.
Устанавливаются git, nginx, PostgreSQL 16/server+client, Python venv/pip,
CA/openssl, SSH client, tar/gzip/curl, certbot/nginx plugin и Python requirements.lock.
БД/API слушают localhost, PostgreSQL настраивается для 1 ГБ RAM,
приложение запускается одним Uvicorn worker под systemd с ограничениями ресурсов.

Тестовый запуск с рабочей станции через runner:

```powershell
pwsh -File scripts/automation/Invoke-RhissethRecovery.ps1 -Operation preflight-test
pwsh -File scripts/automation/Invoke-RhissethRecovery.ps1 -Operation restore-test -ApprovedRef release/0.0.1
pwsh -File scripts/automation/Invoke-RhissethRecovery.ps1 -Operation validate-test
pwsh -File scripts/automation/Invoke-RhissethRecovery.ps1 -Operation reboot-test
pwsh -File scripts/automation/Invoke-RhissethRecovery.ps1 -Operation validate-test
```

Без `-ApprovedRef` восстановление выбирает последний опубликованный Release.
После восстановления проверки обязательны: совпадение таблиц с дампом до запуска,
долговременные данные после запуска, роли, синтетический login/logout/registration,
запрет повышения роли, CSRF, чтение/изменение карты, статика, API, приватные пути,
HTTPS с проверкой доверия и имени сертификата. Синтетические пользователи удаляются,
измененный гекс восстанавливается вместе с updated_at. Сессии могут меняться
при обращении к страницам; первоначальное точное сравнение выполняется до запусков.
После перезагрузки тестовой ВМ повторить validate. Не изменять DNS рабочего домена.

Повторное прямое восстановление того же архива/SHA является no-op и не меняет
данные. Контроллер при обнаружении существующего экземпляра останавливает
автоматическое новое восстановление до preflight; повторные проверки выполняются
отдельно. Частично установленный экземпляр без recovery.json не перезаписывается.
При сбое после установки пакетов они могут остаться установленными: изучить фазу
по журналу, сохранить данные, изолировать/очистить только артефакты Rhisseth или
восстановить снимок тестовой ВМ. Автоматическое удаление неизвестных БД запрещено.
Откат схемы не автоматический: восстанавливать подходящий архив и совместимый релиз
на отдельной ВМ, согласовав потерю изменений после времени копии.

## Домен и HTTPS

Конфигурация на ВМ: `/etc/rhisseth/instance.json`, образец
`deploy/native/recovery.example.json`. Менять `domain`, `tls_mode`, `acme_email`,
`public_ip` (если ВМ за NAT) без редактирования скрипта. В публичном режиме DNS
должен указывать на эту ВМ, входящие 80/443 доступны, заполнен ACME email.
Установка останавливается, если DNS указывает на иной адрес.

```bash
sudo python3 /opt/rhisseth/scripts/automation/rhisseth_deploy.py apply-config --config /etc/rhisseth/instance.json
sudo python3 /opt/rhisseth/scripts/automation/rhisseth_deploy.py validate --config /etc/rhisseth/instance.json
```

Команды выполнять через разрешенный контроллер. Восстановление сохраняет проверенные
target scripts в `/opt/rhisseth/scripts/automation` для дальнейшей эксплуатации.
Скрипт выпускает сертификат через ACME webroot, затем проверяет и применяет nginx.
Certbot timer продлевает сертификат и делает reload nginx через deploy hook.
При ошибке конфигурации прежний vhost восстанавливается. Настройка DNS отдельно.
Тестовый режим использует отдельный self-signed сертификат на домен и IP тестовой
ВМ; он не меняет рабочий DNS и не доказывает выпуск публичного сертификата.
Публичный выпуск/renewal необходимо испытать отдельно на разрешенном домене/ВМ.

## Запуск с другого места и на другой ВМ

Docker не требуется. Контроллер: Linux, Python ≥3.11 с zoneinfo и обновленной
tzdata, OpenSSH client, git, sshpass для password-based доступа (не нужен при
использовании ключей). Для текущего Passbolt-провайдера нужны настроенный Passbolt
CLI, его config и passphrase-файл на runner. Native target scripts используют
Python 3.12 Ubuntu 24.04 и не зависят от Windows/PowerShell.

Скопировать проверенные scripts/automation и tests в отдельный каталог проекта,
создать JSON по `deploy/native/controller.example.json`. Роль `test` обозначает
целевую ВМ, ее IP/username/resource_id меняются в конфигурации. Настройки `instance`
задают домен и TLS. Доступы можно задать через `identity_file`+`username`
(sudo -n на целевой ВМ) либо `credentials_file`: owner-only JSON с `uri`,
`username`, `password`. JSON с паролем хранить вне Git; приватные ключи — отдельно.
SSH host keys должны быть заранее независимо проверены и внесены в known_hosts,
`StrictHostKeyChecking=yes` не отключать. Порт SSH задается `port`.
Для чтения хранилища использовать `automation_identity_file` отдельного ключа.

```bash
python3 scripts/automation/Run-RhissethRecovery.py preflight --controller-config /secure/controller.json
python3 scripts/automation/Run-RhissethRecovery.py restore --controller-config /secure/controller.json
python3 scripts/automation/Run-RhissethRecovery.py validate --controller-config /secure/controller.json
```

По умолчанию `enforce_runner=true`. Внешний контроллер разрешается только для
публичных IP всех настроенных целей с `enforce_runner=false` и локальными ключами/
credentials_file, без обращений к внутреннему Passbolt. Для внутренней инфраструктуры
скрипт требует STU-AUTOMATION-01; WSL/Docker Desktop не обходят эту политику.
Шаблон systemd расписания привязан к текущему пути runner: при переносе изменить
User/WorkingDirectory/ExecStart и добавить `--controller-config`, проверить запуск
службы и права. Переносить секретный storage-key только по защищенному каналу либо
выпустить новый ключ и установить его ограниченный доступ через администратора.

## Отчеты и журналы

Каждая операция ведет Markdown log с UTC/МСК, контроллером, runner, целями,
типом действия, preflight, exit codes, валидацией, изменениями/перезагрузками и
ID Passbolt без значений секретов. Runner logs — внутри проекта в
`reports/automation-logs/YYYY-MM-DD/`; source — `/opt/rhisseth/reports/automation-logs/`;
storage — `/srv/backups/rhisseth/reports/automation-logs/`; target/bootstrap —
`/var/log/rhisseth/reports/automation-logs/`. Ошибка записи лога останавливает мутации.
Отчеты сохраняются в `reports/`; инфраструктурный анализ требует технического `.md`
и управленческого `.docx`. Пересылка другим людям не настроена.

Первый preflight прежней ВМ остановился на 652 МиБ RAM. После изменения адреса
на `10.210.52.56` восстановление 17.09.2026 выполнено при RAM 1902 МиБ.
Проверены данные, роли, API, HTTPS с runner и автозапуск после перезагрузки.
При активном UFW развертывание добавляет только TCP 80/443, сохраняя прочие правила.
Домен и TLS задаются в `/etc/rhisseth/instance.json`; испытательная ВМ использует
тестовый сертификат, публичный DNS не переключался.

Бэкап 17.09 в 06:00 МСК завершился отказом до остановки приложения: исходный
Git checkout содержит локальные изменения. Для восстановления выбран последний
успешный архив 16.09. Предложение `docs/proposals/rhisseth-backup-with-local-worktree.py`
сохраняет локальный код отдельным снимком внутри архива, не применяя его поверх
утвержденной версии. Оно не установлено: автоматическая проверка разрешений
отклонила отправку расширенного незашифрованного payload без явного согласования.
Альтернатива — владельцу сохранить нужные изменения в Git и привести checkout
источника к чистому состоянию. Итоги: `reports/2026-09-17-rhisseth-backup-recovery.md`
и соответствующий `.docx`.

Технические основания: [pg_dump PostgreSQL 16](https://www.postgresql.org/docs/16/app-pgdump.html),
[GitHub Releases API](https://docs.github.com/en/rest/releases/releases),
[systemd timer](https://github.com/systemd/systemd/blob/main/man/systemd.timer.xml).
