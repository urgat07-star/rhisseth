# Краткая инструкция Rhisseth: GitHub, локальный репозиторий и VDS

Запуск меню из корня проекта:

```powershell
.\tools\rhisseth-sync.ps1
```

## 1. Локальная разработка → GitHub → VDS

1. **Пункт 1** — проверить локальный репозиторий, GitHub и VDS.
2. **Пункт 2** — получить последние изменения GitHub.
3. Выполнить и проверить локальную разработку.
4. **Пункт 3** — создать коммит либо релиз и отправить изменения в GitHub.
5. **Пункт 4** — развернуть подтверждённую ветку GitHub на VDS; backup создаётся автоматически.
6. **Пункт 7** — перезапустить службы и проверить сайт.
7. **Пункт 1** — итоговая проверка.

Успешный итог:

```text
LocalEqualsGitHub : True
VdsFilesChanged   : False
Ahead             : 0
Behind            : 0
```

## 2. Дизайнер изменил файлы непосредственно на VDS

1. **Пункт 1** — увидеть точный список изменений VDS.
2. **Пункт 5** — скачать VDS, создать отдельную ветку и коммит, отправить ветку в GitHub.
3. На GitHub создать Pull Request:

   ```text
   base:    batell
   compare: vds/import-ДАТА-ВРЕМЯ
   ```

4. Проверить список файлов. Не объединять Pull Request, если он удаляет или изменяет неожиданные `deploy`, `reports`, `tools`, секреты, `.env` либо другие служебные файлы.
5. Выполнить **Merge pull request** в `batell`.
6. **Пункт 2** — получить объединённые изменения в локальный репозиторий.
7. **Пункт 4** — повторно развернуть зафиксированную версию GitHub на VDS с backup, чтобы GitHub стал эталоном.
8. **Пункт 7** — применить изменения и проверить службы.
9. **Пункт 1** — итоговая проверка; ожидаются `True`, `False`, `0`, `0`, как в первом сценарии.

## Главное правило

Перед пунктами **4** и **7** убедитесь, что нужные изменения уже находятся в GitHub. Если на VDS есть несохранённые изменения дизайнера, сначала используйте пункт **5**, проверьте Pull Request и объедините его.
